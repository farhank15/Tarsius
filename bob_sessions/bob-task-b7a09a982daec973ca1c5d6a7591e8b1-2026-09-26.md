### Why ORDVAL allows DISC orders for suspended accounts

**Short answer: a legal settlement overrode the spec, and the documentation was never updated.**

#### What the code does — [`ORDVAL.rpgle:65-81`](sample-data/ORDVAL.rpgle:65)

The logic runs in two sequential steps:

1. **Lines 65–68** — `$CHKSTATUS` sets `wsResult = 'R'` and returns early if `custStatus = 'S'`. This matches the spec.
2. **Lines 77–81** — Immediately after, a second check tests `suspendedFlag = 'Y'` AND `pOrderType = 'DISC'`. If both are true, it *overrides* the prior rejection, sets `wsResult = 'A'`, and returns early as approved.

Note the distinction: `custStatus` is the account's status code (the `'S'`), while `suspendedFlag` is a separate boolean field on the CUSTMAST record. A suspended account will have both set. The second block fires after the first, so it acts as a deliberate reversal.

#### Why this was added

The code comment at [`ORDVAL.rpgle:73`](sample-data/ORDVAL.rpgle:73) is explicit:

> `Reason: Ticket CS-4471 (2010 class action settlement)`
> `DO NOT REMOVE without legal.`

A class action in 2010 resulted in a settlement that legally required suspended accounts to retain access to discounted (`DISC`) orders. The developer who implemented it documented the ticket reference directly in the source — a rare but very useful practice.

#### Why the spec still says "no exceptions"

The spec at [`order-validation-spec.md:36`](sample-data/order-validation-spec.md:36) was last updated **2015-01-10** — five years after the settlement — yet it still reads:

> *"This rule applies universally. No exceptions exist for suspended accounts under any order type."*

Notably, the spec itself contains an editorial footnote at [line 38](sample-data/order-validation-spec.md:38) acknowledging this:

> *"This statement was true at the time of writing — but ORDVAL.rpgle has since been modified to include a DISC order exception under CS-4471. This documentation was never updated."*

So even the documentation authors knew it was wrong and left a note — but the body of the spec was never corrected.

#### What this means for modernisation

This is exactly why `BR-DISC-EXCEPTION` is flagged **🔴 must-review** with `GOT-001` active. The **code is the legal source of truth here, not the spec.** Any modernised implementation must preserve this carve-out. Removing it to "align with the spec" would be a compliance violation.
